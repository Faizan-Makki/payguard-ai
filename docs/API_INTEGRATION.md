# PayPal API integration notes

Verified against PayPal developer documentation on 2026-10-27. The Transaction Search API documents `GET /v1/reporting/transactions` with OAuth 2.0 client-credentials and the Sandbox URL `https://api-m.sandbox.paypal.com`. The client requests `fields=transaction_info` and `balance_affecting_records_only=N`, maps only ID, initiation time, amount/currency, status and reference, validates page metadata, and retrieves all reported pages. Page size defaults to 100 (the API allows 1–500); a defensive 20-page ceiling (2,000 default-sized rows) raises an error instead of returning an apparently complete partial dataset.

PayPal documents that the API lists transactions from the previous three years, but any individual date range can span at most 31 days. Executed transactions may take up to three hours to appear. This app queries the previous seven days. A populated result therefore depends on real test transactions in the configured Sandbox account and its reporting access; no account history can be inferred from credentials alone.

The Settings connection probe independently verifies OAuth plus a one-hour reporting API query with page size one. A successful probe is distinct from loading dashboard data, and can return zero matching transactions. Dashboard status reports rows loaded and malformed rows skipped. The configured Sandbox credentials successfully authenticated, but the Transaction Search request returned HTTP 403 and the OAuth response did not grant the required reporting search scope. The UI surfaces sanitized errors and never swaps in demo data under a Sandbox label.

Hackathon rule check: the official rules require meaningful PayPal Sandbox integration and AI use, a functional demo, public source repository with an open-source license, and a public YouTube video under three minutes. The local deterministic fallback is not represented as provider-backed AI. Credentials and real responses remain to be supplied and tested. See [`SUBMISSION_CHECKLIST.md`](SUBMISSION_CHECKLIST.md).

# PayPal Sandbox checkout

PayGuard's optional fixed USD 1.00 checkout uses PayPal Orders API v2 only on the official Sandbox API host. The server creates an order with `intent=CAPTURE`, stores its order ID and per-operation `PayPal-Request-Id`, and returns only PayPal's Sandbox approval URL to Streamlit. After buyer return, the browser-supplied order token must match the order stored against the random state nonce. PayGuard fetches the order from PayPal and captures only an `APPROVED` order. It persists a transaction only after PayPal reports the order and exactly one capture as `COMPLETED`, with the expected amount and currency. The cancel path fetches status but never makes a capture request.

Set `PAYPAL_RETURN_URL` and `PAYPAL_CANCEL_URL` to the app URL. Local defaults are `http://localhost:8501/`; hosted instances require HTTPS. Checkout records live in the configured SQLite database and expire after 30 minutes. The browser never receives the Client Secret or OAuth access token. The capture record omits payer identity and is sent only to the existing deterministic risk rules. This local demo flow is not suitable for multi-instance or ephemeral production storage.

Official documentation: [Orders API integration](https://developer.paypal.com/api/rest/integration/orders-api), [Create order](https://developer.paypal.com/docs/api/orders/v2/#orders_create), [Capture order](https://developer.paypal.com/docs/api/orders/v2/#orders_capture), and [REST idempotency](https://developer.paypal.com/api/rest/reference/idempotency/).
